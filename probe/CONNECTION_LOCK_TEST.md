# FreeClip 2 本次连接锁定：Windows 实发验证

验证日期：2026-10-22（北京时间）。目标耳机 `C0:DA:5E:**:**:**`，目标电脑 `E4:60:17:**:**:**`。本轮用户明确同意测试，并在手机上先关闭锁定。

## 结果

- 电脑通过 RFCOMM channel 1 发送锁定指令后，耳机给出校验通过的对应回复，设备枚举中的电脑 TLV `0x0d` 从 `00` 变为 `01`。
- 用户确认手机华为 App 的“本次连接锁定”已打开，手机声音不能抢占电脑音频。
- 电脑随后发送解锁指令，耳机给出对应回复，电脑 TLV `0x0d` 从 `01` 回到 `00`。
- 用户确认手机开关已关闭，音频恢复正常。
- 本轮最终状态为解锁，手机与电脑的蓝牙连接均保留。

因此，本机和当前 FreeClip 2 固件上的电脑锁定/解锁控制及音频效果已验证。未验证其他型号、固件，或断线自动解除的所有场景。

后续边界修正：用户于约 11:05 报告首次播放时锁定出现音频卡顿、耳间不同步及 Windows 输出消失。上述单次短时成功只证明当时的功能行为，不证明首次使用和持续播放稳定性。现已保存 Windows 事件和手机 HCI 原始证据；调整了命令确认与等待顺序，但未重新触发故障、不能声称音频稳定性已修复。

11:30 再次故障：调整后的版本仍在播放中锁定后出现无声，约 10 秒后 Windows 输出变为 UNPLUGGED。手机解除锁定未恢复；重开 Windows 蓝牙使输出重新出现但仍无声，重新打开播放器也无效。经用户授权仅重启 Audiosrv 后，用户确认声音恢复。记录位于 `.scratch/audio-lock-incident-20261022-1130/FINDINGS.md`。因此锁定实现的播放稳定性尚未解决；本轮只采集现有状态和恢复过程，没有重新发送锁定指令。

## 指令与状态

管理命令：`0x2b33`。TLV 的值为目标设备在耳机枚举表中返回的 6 字节原始 MAC，不应按显示字符串顺序直接拼接。

| 操作 | TLV id | 本次目标值 | 耳机响应字段 |
|---|---|---|---|
| 锁定 | `8` | `xx xx xx 17 60 e4` | `0x1e=08`、`0x1f=00` |
| 解锁 | `9` | `xx xx xx 17 60 e4` | `0x1e=09`、`0x1f=00` |

实际发送：

- 锁定：`5a000b002b33080697258d1760e4f32d`
- 解锁：`5a000b002b33090697258d1760e4b4fe`

设备表查询：`0x2b31`，电脑行 TLV `0x0d` 在本轮与锁定状态同步改变，可用作锁定状态读取依据。

没有发送抓包中伴随出现的 `0x2b32` 全零首选设备请求；锁定和解锁均独立生效。试验前后首选字段保持 `00`，未验证已有其他首选设备时的交互规则。

## 证据与复现

- 锁定：`../.scratch/connection-lock-on-20261022-102721.json`（发送于 10:27:23）。
- 解锁：`../.scratch/connection-lock-off-20261022-102822.json`。
- 第一次尝试在建立 SPP 连接时返回 Windows 10048，未发出控制报文。随后重试连接成功；没有重复发送已成功的修改指令。
- `connection_lock_test.py` 提供 `status`、`on`、`off`。默认只读；写入前校验目标电脑确实在耳机表中且已连接，锁定前还要求双设备已连接。不会清除首选、取消配对、断开设备或自动重试修改。
- `--self-test` 校验生成帧与手机抓包完全一致，并拒绝 CRC 错误的回复。

Windows 控制程序尚未接入锁定按钮，本轮仅通过独立试验程序验证。
