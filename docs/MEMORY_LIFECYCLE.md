# 空闲内存与界面生命周期

本版仍采用单进程 WinUI。托盘消息窗口、共享耳机数据及运行时常驻；菜单和设置的控件树不再负责持有后台服务。

2026-10-23 用户确认继续采用单进程，优先控制打开设置时的总占用，接受关闭后的自然延迟回收；不拆分设置进程，不恢复强制 GC 或工作集清空。菜单仍保留 7 分钟缓存。

- 普通冷启动不创建耳机面板、阴影图片、菜单动画或菜单材质。
- 首次打开（包括缓存回收后）：先创建控件，通过 DWM cloak 保持窗口不可见且不激活，等待 Loaded、阴影资源以及布局准备完成，再解除 cloak 并执行原有平移动画。准备阶段不等待蓝牙查询。准备超时或取消时隐藏并清理，下一次点击可重试。
- 菜单收起后缓存 7 分钟，以单调计时器计算；每 15 秒检查一次，正常会在 7 分钟至 7 分 15 秒之间回收。重新打开取消旧期限，下一次收起重新计时。等待加载、显示、动画或确认操作期间不会回收。
- 回收时移除控件树、停止绑定和动画、退订系统颜色事件、释放光标、断开材质和阴影资源。共享数据不受影响，设置窗口也不持有菜单方法委托。
- 设置在原生窗口关闭前停止绑定、注销窗口和尺寸事件、取消窗口等待与型号更新、停止页面动画、解除自定义标题栏注册，断开 Mica 和窗口内容；Closed 保留幂等兜底。已经提交的耳机操作由后台完成，不因关闭设置而中断写入。异步回调关闭后不更新窗口。是否完全回收仍须以日志或内存分析确认。
- 托盘后台只读取已使用的电量命令，不查询设备表、不主动重连、不发送修改指令。打开数据界面仍执行完整读取，电量查询不会将旧设备表误标为完整。
- 已撤掉强制 GC：实际日志显示两轮 GC 后设置窗口和内容仍存活，不能用重复 GC 解决引用保留。现在只在关闭后的空闲阶段被动记录内存，不强制回收、不清空工作集。
- `UI MEMORY` 日志分别记录托管字节、GC 提交量、进程私有提交量和工作集；对关闭的设置窗口、内容树及回收的菜单使用弱引用记录 `managedAlive`。`False` 表示托管对象已回收，不能据此声称所有原生资源均释放；`True` 需要进一步分析引用或等待中的任务。菜单缓存期内仍占内存属于既定行为。

## 验证边界

代码检查和编译不证明像素表现或实际节省的 MB。没有执行自动 UI、真实耳机或注销登录测试。

手动验收建议：

1. 退出旧版，普通冷启动只出现托盘。日志中不应出现 `Menu UI created on demand`，直到主动打开菜单。
2. 首次打开以及回收后重新打开时，不出现空白菜单；原有动画、自动收回、四边阴影和浅深主题正常。
3. 收起 6 分钟后重开复用缓存；重新收起后超过 7 分 15 秒，日志出现 `Menu UI released`；下一次打开重新创建。
4. 菜单收起等待回收期间打开设置；回收后设置电量和操作仍正常。设置关闭日志显示已解除绑定与取消等待。
5. 连续开关菜单、切换页面、打开关闭设置多轮，并测试准备期间再次点击、打开设置及退出。
6. 在相同托盘电量设置下比较冷启动、打开设置/菜单、关闭并空闲后的私有提交量、工作集和句柄数量。观察多轮后是否达到稳定平台；不要仅以一次工作集变化判断泄漏或收益。

DWM cloak 的官方语义：窗口不可见，但继续参与合成。参考 https://learn.microsoft.com/en-us/windows/win32/api/dwmapi/ne-dwmapi-dwmwindowattribute 。

## 2026-10-25 闲置后重开菜单的原生崩溃

用户报告后台占用有时降至约 7 MB，之后点击托盘偶发闪退。只读分析已有日志和 Windows 崩溃转储，未启动应用、强制 GC、操作界面或发送耳机指令。

- Windows 事件确认 10 月 24 日 18:17:56、10 月 25 日 12:13:37 和 12:45:57 均在 `Microsoft.UI.Input.dll`（10.0.27200.1054，偏移 `0x9f853`）发生 `0xc0000409`。子码为 `FAST_FAIL_FATAL_APP_EXIT`，附加错误为 `0x8001010e`（错误线程），不能把这一事件泛称为内存不足或栈溢出。
- 12:13:37 对应 PID 10336：12:11:27 已回收菜单；再点击托盘，重建菜单之后中断。12:45:57 对应 PID 31316：12:23:15 回收菜单后仍继续运行了二十多分钟。
- 两份转储均确认故障线程是 `.NET Finalizer`。利用匹配的微软公开符号，原生栈为 `ContentExternalBackdropLink::Release → 析构 → Dispose → CloseHelper<IContentSite> → FailFast_Hr`；PID 10336 的托管栈为 `WinRT.IObjectReference.Finalize()`。证据存放在 `.scratch/tray-reopen-diagnostics-20261025/`，原始转储留在用户的 `LocalAppData/CrashDumps`，不打包发布或上传。
- `PanelAcrylicBackdrop` 原先仅移除并释放 `DesktopAcrylicController`。元素连接对象仍可能保留在托管投影里，随后由终结器线程触发原生析构。这与转储吻合；无法从转储还原用户看到的 7 MB 具体统计口径，也不能断言每次内存回落都触发此问题。
- 修复为专用的 `DetachForRetirement`：先在界面线程保留当前目标，清空 `SystemBackdrop`，让控件解除材质和视觉连接，再通过其 `IClosable`（C# `IDisposable`）显式关闭背景连接。之后自然 GC 只需回收已关闭的包装对象。此入口仅用于面板最终回收，不用于给存活元素切换背景；成功日志为 `Panel backdrop link closed on UI thread.`。
- 保留单进程、七分钟菜单缓存、加载完成才显示和原有阴影/亚克力；不引入强制 GC、工作集清空或常驻旧菜单。
